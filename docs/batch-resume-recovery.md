# 批量恢复与互斥修复

恢复任务先切换并校验包含今天的近180天范围，再按计划ID逐页批量开启和读回状态。暂停流程沿用原有日期范围。扫描检测重复分页，未完整读完时保留“扫描不完整”，不把缺失判为完整扫描未找到。

批量已成功的计划不再重试。只有已定位且动作失败的计划进入精确重试，每部门最多3条、总重试窗口120秒、单条最多45秒；其余恢复票继续保留，后续必须先查平台现状。未找到、系统暂停、未知状态、扫描异常都不逐条重搜。人工白名单始终排除。

启停互斥锁等待超时直接失败退出。只有获得锁的进程才能写忙标；退出仅删除自己持有的忙标，先清标再释放锁。等待表格轮询或日报超时同样退出。

部署前需停止已载入旧代码的冲突任务，确认对应进程退出后才清理遗留忙标。恢复时重新查询平台，不能根据中断前日志直接假定开启成功；成功记录按现有对账机制扫描落库。恢复队列不因停止任务而清空。

验证：使用项目便携Python并显式指定仓库模块路径，运行 `巨量千川.test_batch_resume`、`巨量千川.test_plan_metrics_overview`、`巨量千川.test_lifecycle.OldPoolResumeQueueTests`，31项通过；中午及17点串行链9项通过，CDP与会话准备10项通过，定向检查合计50项通过。扩展150项测试有6项旧ROI口径失败，与修改前118项中的6项失败完全相同，没有新增失败。

中午注册统一使用 `noon_report_resume.py`，停用旧的独立 `wecom_report_noon`，日报注册脚本不会再建回并行任务。恢复后的全量对账在所有已开启目标读回为投放中且没有扫描错误时结束；有不一致才继续最多三遍。

平台日期导航会恢复到全店托管页；共用总览和日期入口现在软切回计划页，批量扫描前校验表格就绪，避免把无计划表误判为目标不存在。现场只读验证：三部切回后由无表变为98行，未进行任何计划参数修改。

系统暂停按解析后的 `pause_category=system_pause` 判断，即使状态首行只有“已暂停”也不点击、不进入精确重试。

二部平台会在hash软切之后再次恢复托管页；切页函数先点击实际“商品自选”页签，使SPA持久状态同步，再使用hash兼容兜底。

批量按页复用表头映射，避免每一行重复读取数十列表头。现场只读测量中，单次表头读取约20.4秒、复用表头后的行解析约0.09秒；耗时随页面负载变化。
